首先要明确的一点是，和windows，linux不同，安卓几乎没有有那种裸奔的可执行文件，而都是**以apk为基本单位的一个个软件包**。这并不代表安卓不能跑那种单个的可执行文件，实际上安卓走的是linux内核，原生跑个ELF理论上是可行的，但是实际上可能会遇到各种阻碍，比如运行时很乱套，入口封的很死，权限把的很死等等，具体的这些后面...也许也不会讲到（汗）

所以入手安卓逆向先从apk搞起，先简单分析一下整个包里有什么东西。

## apk结构

作为一个软件包，apk内部有一堆乱七八糟的东西，大致可分为三部分：**可执行部分、基本信息部分、以及资源**。

### 可执行部分（`classes.dex`、`lib/`）

对于安卓来说，最大痛点就是设备种类很多，硬件、架构、指令集等各种东西都会导致环境出现极大差异，这时候如果给每一个不同的环境都发行一套专用的安装包，维护成本将会非常疯狂，因此安卓采用了一种非常天才的解决方案：**虚拟机 + native层**。

应用的主要业务由**java或kotlin**编写，编译为`.class`文件，然后用安卓sdk转换为dalvik字节码（以`.dex`格式存储），如果`.dex`文件过大则需要分块。在旧版本中由dalvik虚拟机边解释边执行，5.0之后开始通过安卓运行时（ART）预先将`.dex`文件进一步编译为`.oat`机器码，7.0之后改为混合采用解释执行与编译执行。

底层逻辑由native层实现，其实就是大家很熟悉的本地库，由**C或Cpp**编写，编译为`.so`文件，存储在`lib/`目录中，一般应用会打包好几个不同架构的库。

将两者联系起来的东西叫做**java本地接口（JNI）**。简单举例，敲java代码时，如果需要调用一个本地库的方法，在声明的时候加个`native`修饰，写成空方法，执行到调用这个方法的时候虚拟机便会通过本地接口跳转到native层执行。

### 基本信息部分（`META-INF/`、`AndroidManifest.xml`）

这一部分记载了整个应用的相关信息，可以理解为整个apk的文件头。

`AndroidManifest.xml`是应用的**清单文件**，记载了程序包名、权限、组件声明、sdk版本等信息，从这个文件就可以分析出程序的入口等关键信息。值得一提的是虽然是`.xml`文件，但是经过了aapt工具的编译，其实是一份二进制文件，需要经过反编译处理。

`META-INF/`内记载了应用的签名和校验信息，主要为了**防止apk被篡改**，其中包括对整个apk内容的摘要，以及摘要的摘要等一系列验证文件。但凡更改了apk内任何一个部分，都会导致验证失败，因此patch后的apk需要重新打包签名，而有的应用还会自带签名校验逻辑，patch之后可能会导致校验失败，比较棘手。

### 资源部分（`res/`、`resources.arsc`、`assets/`）

对于一个应用需要用到的资源，大致可分为两类：一类是大家约定俗成的一些东西，配好塞进包里就能自动加载；另一类是自定义的东西，得自己说明怎么加载，如何布局。

前者就是`res/`里的东西，主要有布局、颜色、尺寸、字符串、以及一部分图片资源（比如应用图标）。这些文件在打包时大多会经过统一编译、优化，变为带**有索引值的二进制资源**。

后者就是`assets/`里的东西，主要有字体、图片、音乐等资源，打包时一般不会编译，直接以**原始资源**的形式包入apk。

而`resources.arsc`就是一份资源映射表，记载了编译后的资源（或资源位置）与索引值之间的关系。

## 静态分析指北

### 解包

apk本质就是一个压缩包，理论上是可以直接解压的，但是有些东西在打包时会编译，搞得很乱套，因此除了暴力解压之外需要一些其他的分析方法。这里介绍两个工具：**jadx和apktool**。

jadx是一个类似ida的逆向工具，如果用它打开一个apk，他会直接给你列出当前包内的结构，并尝试反编译`.dex`文件（生成java伪代码）以及一部分`.xml`文件（还原成原始的文本格式）。推荐使用jadx-gui，在github直接下载即可。使用方法比较简单粗暴，直接将apk拖进去即可。

apktool是一个专门用于解包打包签名的工具，相比于jadx，他的解包会更智能一点，主要体现在其会去尝试还原解包前的模样。举个例子，像字符串这种二进制资源，编译优化之后就不在`res/`里了，而是直接塞进`resources.arsc`中的一个叫字符串池中。如果用jadx，他不会尝试将字符串剥出来；而apktool就会还原出完整的`strings.xml`文件。推荐使用`.jar`文件，在github直接下载即可。在终端运行以下命令，就会将解包后的文件夹存储在当前目录中了：

```terminal
java -jar <apktool的目录.jar> d <apk的目录.apk>
```

### smali汇编简介

smali汇编就是人类可读的dalvik字节码，当你用apktool解包时，`classes.dex`便会变为一堆`.smali`文件。至于为什么我们需要分析smali汇编，而不是直接看java伪代码...最主要的原因是kotlin有许多他自己的特性，虽然最后都是编译成dalvik字节码，但是反编译出来的java伪代码未必能完整还原其逻辑，因此我们偶尔也需要分析能完整还原逻辑但可读性不是那么好的smali。。。

smali中存在变量类型，但是用简称表示，具体的简称如下：

```text
Java:             Smali:
boolean           Z
byte              B
short             S
char              C
int               I
long              J
float             F
double            D
void              V
String            Ljava/lang/String;
int[]             [I
String[]          [Ljava/lang/String;
int[][]           [[I
Object            Ljava/lang/Object;
```
